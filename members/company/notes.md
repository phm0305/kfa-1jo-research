## 재개 진단과 남은 작업

### 실행 경로

가이드 명령은 레포 루트에서 `py run.py --member company --stock 004370 --year 2025`다. `--member company`는 `members/company/prompts/`를 공통 `prompts/`보다 먼저 검색해 멤버용 company 지시서를 고른다. 현재 나머지 파트·센터장·품질 점검·반대신문 지시서는 공통본에서 읽는다. 결과는 `members/company/runs/<종목>_<연도>_<월일_시분>/`에 저장한다. 새 폴더에는 직전 동일 종목·연도의 첫 바퀴 JSON을 복사하고 질문이 정확히 같으면 저장 답을 재사용한다. `dummy_data.csv`가 있으면 CLI가 company에만 연결한다.

CLI는 데이터 수집 → 산업·기업·재무·밸류에이션 원고 → 센터장 → 전체 숫자 대조 → 품질 점검과 필요한 재작성·재대조 → 반대신문 → 결과 저장을 실행한다. `--member company`는 지시서 선택과 결과 경로를 정한다. company만 작성하거나 숫자 대조부터 재개하는 옵션은 없다.

이번 직접 호출은 같은 `pipeline.run`을 사용했다. 공통본은 `prompts/`만, 수정본은 `members/company/prompts/`와 `prompts/`를 순서대로 검색했다. 실행 폴더 이름을 직접 지정하고, 공시 캐시를 실행 폴더에 두며 동일한 데이터 묶음을 공유했다. 재시도 때는 저장 묶음과 일치하는지 확인하고 HTTP 요청에 10분 제한을 적용했다. 수정본의 동일 질문에는 산업·밸류에이션 캐시를 재사용했다. 직접 호출에는 더미를 넘기지 않았다.

### 기록된 오류

| 코드 | 확인된 기록 | 해석 |
|---|---|---|
| 429 | 수정본 센터장 실행 로그에 기본 모델의 요청 한도 재시도 메시지가 있다. 저장된 최종 검증 기록에는 예비 모델 503이 남았다. 429의 제공자 상세 쿼터 메시지는 확인되지 않는다. | 호출 제한이다. 분당·일일 한도 중 어느 쪽인지는 기록으로 판단할 수 없다. |
| 503 | 공통본 숫자 주장 추출 기록과 수정본 company 응답 기록에 기본 모델의 `UNAVAILABLE`이 남았다. 수정본 센터장 최종 오류는 예비 모델 `503 UNAVAILABLE`이며 제공자 메시지는 높은 요청량을 언급한다. 공통본 첫 시도의 후속 숫자 추출에서도 503이 관찰됐다. | 서비스 요청 처리 실패다. API 키 오류나 쿼터 소진을 입증하지 않는다. |
| 504 | 공통본 숫자 대조 재시도의 기본 모델 오류는 `DEADLINE_EXCEEDED`이며 제공자는 처리 기한 만료를 기록했다. | 시간 초과다. 현재 엔진의 429·500·503 재시도 목록에는 504가 없다. |

### 최소 복구 방법

1. **저장 초안의 숫자 대조만 진행할 경우** 두 `company_r0.json`과 동일 입력을 보존하고 별도 결과 폴더를 사용한다. CLI에 검증 전용 모드는 없다. 기존 `claims_prompt`·`ask_claims`·`load_claims`·`check_claims`와 발췌 대조를 얇은 오프라인 재개 절차에서 호출할 수 있다. 수치 판정 자체는 로컬 처리다. 공통본의 전체 `claims_r0.json`에는 주장이 저장돼 있으므로, 기존 귀속 규칙으로 company에 연결되는 주장과 누락을 확인하는 데 먼저 재사용한다. 수정본에는 주장 추출 응답이 없다. 두 초안을 같은 추출 조건으로 판정하려면 company 원고만 대상으로 동일 검증 모델로 각각 한 번의 주장 추출 호출이 필요하다. 이 방식의 결과는 별도 company 숫자 대조 기록이며 전체 품질 점검·반대신문·최종 리포트 완료와 구분한다.
2. **판정 입력을 보존한다.** `bundle.txt`는 표시용으로 일부 값이 반올림되므로 그대로 원정밀 데이터로 쓰지 않는다. 공통본 `claims_r0_기록.json`의 저장 질문에는 당시 숫자 대조에 전달된 공통 표와 지표 표가 있다. 이 표의 수치·ID와 묶음의 지표 상태·입력 ID·출처·발췌를 맞춰 엔진 입력을 복원한다. 정밀도, 출처 연결 또는 누락 처리의 동등성을 확인하지 못하면 판정을 확정하지 않고 동일 원본 묶음을 복구한다.
3. **지시서 효과를 공정하게 비교할 경우** 기존 초안 모델이 다르므로 두 company 원고부터 같은 실제 모델로 다시 생성해야 한다. `run.py`에는 모델 지정 및 폴백 해제 옵션이 없다. 승인 후 별도 실행 세션에서 런타임 모델을 하나로 제한하고 다른 모델 응답이면 중단하도록 설정할 수 있다. 저장 답은 질문 문자열만으로 재사용 여부를 판단하므로, 이전 모델의 company·숫자 추출 캐시는 그대로 넣지 않고 사용할 모든 캐시의 실제 모델을 확인한다. 모델이 응답하지 않으면 다른 모델 결과와 짝짓지 않는다. 기존 실행 폴더와 원고는 보존한다.
4. **정상 리포트 완료가 목표인 경우** 새 실행 폴더 두 곳에서 같은 입력과 모델로 전체 파이프라인을 마친다. 동일 질문으로 확인된 다른 파트 답을 재사용할 수 있다. 새 company 원고에 의존하는 센터장, 전체 숫자 주장 추출, 품질 점검, 필요 시 재작성과 재검증, 반대신문은 새로 호출해야 한다. 공통본과 수정본의 질문이 우연히 동일한 단계만 재사용 대상으로 삼는다. 정상 완료 시 `report.md`, `report.html`, `verification.md`가 생성되고 작업 기록으로 `bundle.txt`, 단계별 응답 및 호출 기록 JSON, `check_r*.md` 등이 남는다. PASS·REVIEW·FIX는 새 검증의 company 행만 집계한다.

이번 진단은 저장 파일과 코드 읽기로 수행했다. 추가 모델·데이터 API 호출, 리포트 재실행, 검증 실행은 하지 않았다.

## 동일 모델 재개 결과

농심(004370) 2025년 공통본과 수정본의 기존 실패 폴더를 보존했다. 새 폴더의 고정 모델은 `gemini-3.8-flash`이며 폴백과 자동 재시도를 껐다.

- **완료** — 기존 두 입력 파일이 바이트 단위로 일치했다. 공통본의 저장된 검증 질문에서 원정밀 재무·지표를 복원했고, 원정밀 검증 표와 표시용 데이터 묶음이 모두 저장본과 일치했다. 데이터 API 호출은 없었다. 질문과 모델이 일치한 산업·밸류에이션 캐시를 새 폴더에 보존했고, 공통본의 산업 답변을 재사용했다.
- **중단** — 공통본의 첫 `company_r0` 요청이 Gemini 503으로 실패했다. 전체 HTTP 요청은 **1/20회**이며 재시도하지 않았다. 검증 기록은 저장됐다. 오류 뒤 임시 HTML을 만드는 과정에서 복원 데이터의 출처 열이 빠져 HTML 출력도 중단됐다. 로컬 재개 스크립트에 해당 열을 보완했고 API 없이 입력 일치를 다시 확인했다. report.html 생성은 재실행에서 확인해야 한다.
- **남은 작업** — 공통본 company부터 재개한다. 수정본에는 캐시를 준비했으며 모델 호출은 시작하지 않았다. 두 company 원고, 센터장, 숫자 대조, 품질 점검 및 필요한 재작성·재대조, 반대신문과 최종 출력을 완료해야 한다.
